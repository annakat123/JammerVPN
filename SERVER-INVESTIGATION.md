# Сервер: задержка мелких ответов и переполнение очереди

## Воспроизведено в изоляции

Сравнивались копия исходного релиза сервера и собранная версия с небольшими правками. Оба настоящих сервера запускались по очереди в отдельных Linux network namespaces; Python-клиент выполнял штатные X25519/HKDF/AES-GCM и обмен ICMP через настоящий TUN внутри модели. Два направления veth имели по 20 мс задержки. Рабочий VPN, его firewall и интерфейсы не менялись.

### Nagle и NoDelay

Клиент отправлял два маленьких пакета с интервалом 5 мс. Медианы восьми повторов:

| Сервер | Первый ответ | Второй ответ |
|---|---:|---:|
| Исходный релиз | 40,72 мс | 120,91 мс |
| `NoDelay = true` | 40,74 мс | 45,70 мс |

Это воспроизводит дополнительное ожидание маленького ответа при сочетании Nagle и отложенного ACK. Изолированный результат не является обещанием такого же улучшения скорости или пинга каждого живого соединения. Описание [Socket.NoDelay в Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.socket.nodelay).

### Очередь при обратном давлении

В отдельном стресс-тесте задержку netem убрали. Клиент намеренно ограничил приёмный буфер и не читал ответы во время отправки 10 000 пакетов по 1400 байт. Получено 1042 ответа; 8958 ответов отсутствовали. TUN принял все запросы, его счётчики отбрасываний остались нулевыми. Добавленный счётчик отказов `TryWrite` показал ровно 8958.

Так подтверждено молчаливое отбрасывание внутри приложения при заполнении очереди на этом искусственном тесте. **Это не 89,58% потерь обычного VPN, игры или интернет-канала.** В живом соединении переполнение необходимо измерять отдельно.

## Минимальные изменения сервера

- `Server.Tcp/Program.cs`: у принятого TCP-сокета включён `NoDelay`. Адрес клиента записывается до запуска обработчика, который может закрыть сокет; это устраняет обнаруженную гонку с `ObjectDisposedException`.
- `TunDispatcher.cs`: отказы записи в очередь теперь считаются. Предупреждение ограничено одним на 10 секунд для клиента; суммарное число выводится при отключении. Отказ может означать переполнение или закрытие очереди.
- Проверка 150 быстрых отключений завершилась успешно, после неё сервер ответил на контрольный запрос.

Ёмкость очереди и политика отбрасывания пока не изменены. Нельзя просто заблокировать общий TUN-reader на одном медленном клиенте: это остановит обработку остальных клиентов. Увеличение буфера также не объявляется исправлением — оно может увеличить задержку очереди. Формат протокола и шифрование не менялись.

## Воспроизведение

Нужны Linux с root/network namespaces, `ip`, `tc`, Python 3 и `cryptography`. Подготовить отдельную папку непосредственно в `/var/tmp` с именем `jammer-isolated-...`: положить туда `baseline` (проверяемый исходный сервер), `candidate` (собранный сервер), `isolated-server-check.py` и `probe-isolated-jammer.py` из `tests`. Оба бинарника должны быть исполняемыми.

```sh
python3 /var/tmp/jammer-isolated-example/isolated-server-check.py /var/tmp/jammer-isolated-example
```

Сценарий удаляет только созданные им namespaces и завершает тестовый процесс. Вывод и файлы тестовой папки можно сохранить для разбора. Тест намеренно создаёт обратное давление; для него не нужны публичные порты или правки firewall.

Сборка кандидата:

```powershell
dotnet publish source/Jammer/Server.Tcp/Server.Tcp.csproj -c Release -r linux-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -o build/JammerServer
```

Self-hosted сейчас привязан к исходному релизу Vimer v0.1.0 и его SHA-256; новые серверные изменения не выдаются за уже включённые в тот сторонний бинарник. Для применения нужен собранный сервер. Общая задача нестабильности скорости [#3](https://github.com/annakat123/JammerVPN/issues/3) остаётся открытой.

## Пакетная отправка: проверено и включено в исходники

`PacketSender` забирает до 16 пакетов, **уже находящихся** в очереди. Каждый шифруется прежним AES-GCM и получает прежний четырёхбайтовый заголовок; несколько последовательных кадров записываются в один буфер на соединение. Ожидания для накопления группы нет. Частичная отправка досылается циклом. Логика `Crypto.cs` не менялась.

Проверка TCP-совместимости без привилегий и изменений маршрутов:

```sh
dotnet run --project tests/Jammer.PacketChecks -c Release
```

Проверяются немедленная отправка единственного пакета при открытой очереди, 1024 пакета смешанного размера, сохранение содержимого и порядка, замедленное чтение с малыми socket-буферами и EOF. Читатель использует прежние `Frame.ReadFrameAsync` и AES. Малый буфер создаёт обратное давление; тест не утверждает, что ОС обязательно вернула частичный `SendAsync` в каждом запуске.

В модели с настоящим внутренним TCP, двумя Linux TUN, RTT около 40 мс и ограничением 300 Мбит/с выполнен порядок A–B–B–A. Клиент и сервер модели делили один vCPU; это сравнение реализаций, а не прогноз скорости Windows.

| Метрика | Прежняя отправка, два прогона | Пакетная отправка, два прогона |
|---|---|---|
| Полезная загрузка, Мбит/с | 125,93 / 122,17 | 161,34 / 161,48 |
| Средний пинг за окно теста, мс | 90,01 / 92,68 | 54,70 / 52,52 |
| Аллокации сервера на 75 МБ полезных данных, МБ | 455,98 / 456,01 | 367,52 / 367,33 |
| CPU сервера user+system, с | 1,88 / 2,00 | 1,35 / 1,25 |

В каждом прогоне ping дождался всех 30 ответов, отказы очереди были нулевыми. Выигрыш в модели около 30%, аллокации меньше примерно на 19%. Прототипы сокращения аллокаций LinuxTun, буферизованного чтения, synchronous continuations и UDP не дали достаточно устойчивого результата и в продукт не включены. Эксперимент с изменениями AES отменён; исходное шифрование сохранено.

## Живой канал: одной пакетной отправки недостаточно

На реальном соединении пакетная отправка с CUBIC дала только 57,37 и 53,91 Мбит/с. Поэтому модельный выигрыш не выдаётся за результат реального канала. В снятом состоянии внешний TCP имел `cwnd` около 185–342 сегментов при RTT 38–41 мс и MSS 1460 байт: оценка `cwnd × MSS / RTT` согласуется с ограничением порядка 54–100 Мбит/с. Окно получателя было значительно больше.

В **том же установленном соединении**, без замены клиента, глобальных sysctl и перезапуска службы, изменялся только серверный TCP congestion control:

| Состояние | Загрузка, Мбит/с |
|---|---:|
| BBR, первый прогон | 237,98 |
| Возврат CUBIC, первый прогон с оставшимся большим окном | 177,32 |
| CUBIC, следующий прогон | 75,79 |
| Возврат BBR | 208,15 |
| BBR, более поздний контроль после простоя | 169,90 |

Каждый запрос: три параллельных HTTPS-потока, суммарно 150 МБ, фиксированный IPv4 endpoint Cloudflare, FRA, все данные получены. Это короткие собственные HTTP-тесты, не Ookla. Обратимость результата подтверждает вклад внешнего TCP; она не доказывает единственную причину всех просадок. [Описание BBR авторами](https://research.google/pubs/bbr-congestion-based-congestion-control/).

В последнем контрольном окне средний пинг через TUN был 85,18 мс, максимум 370 мс; напрямую 39,79 мс. Через TUN 100/100 ответов, напрямую 98/100. Это наблюдение за конкретным окном, а не постоянный процент потерь канала. Отдача в отдельных последующих тестах дала 38,25 / 85,42 / 53,54 Мбит/с. В окне двух повторов отдачи все три направления ping получили 60/60 ответов; средний пинг TUN 91,95 мс, максимум 311 мс. Отдача и loaded latency **пока не исправлены**.

Windows-клиент остаётся с CUBIC; серверный BBR управляет отправкой сервера, а не алгоритмом отправителя Windows. Общие TCP-параметры Windows не менялись. Наблюдение сегментов вне порядка на принимающей стороне не локализует причину и не равно проценту потерь игровых пакетов. Сохранение исходных TCP-пакетов в одном TCP-туннеле также оставляет [ограничения TCP-over-TCP](https://www.wireguard.com/known-limitations/).

## Необязательный BBR на Linux

Собранный из этих исходников сервер поддерживает переменную окружения:

```ini
[Service]
Environment=JAMMER_TCP_CONGESTION=bbr
```

Её можно задать через `sudo systemctl edit jammer.service`. Она применяется при следующем запуске службы; плановый restart прерывает текущие VPN-сеансы. Проверьте наличие BBR в вашем ядре и журнал после запуска. Код задаёт алгоритм только TCP-слушателю; принимаемые сокеты наследуют его. Без переменной используется алгоритм системы. При отказе ядра сервер пишет предупреждение и продолжает с системным алгоритмом. Глобальный `net.ipv4.tcp_congestion_control` код не меняет.

На проверенном сервере для текущего процесса BBR установлен непосредственно на слушателе и активном сокете; наследование проверено новым соединением. Сборка с выбором BBR при старте проверена отдельно в namespace и подготовлена для следующего штатного запуска, чтобы не обрывать пользовательский чат. Эта особенность развёртывания не заменяет проверку будущего рестарта рабочей службы.

Следующие отдельные задачи: сопоставить внешний TCP с двух концов при отдаче, измерить возраст пакетов в очереди, проверить более длительную смешанную нагрузку и доставку новой серверной сборки через Self-hosted. Остальная частичная отправка в `Core/Frame.cs` и наблюдение исключений в обработчике сессии остаются отдельными задачами корректности; текущая правка не выдаётся за их исправление.
